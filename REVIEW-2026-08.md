# nixgg Improvement Proposal

## 1. Verdict

The project's central invariant — native and sandbox modes emit byte-identical `.drv`s — is currently **violated for a real, reachable input**: a flag containing a literal single quote breaks native mode outright (unparseable bash) while sandbox mode emits valid script text. The 81 currently-pinned drvs never trip this because none of their flags contain an apostrophe, so `tests/drv-equivalence.sh` is silently blind to it. The single highest-leverage change is to close that gap and, in the same motion, stop relying exclusively on a multi-minute, remote-builder-dependent integration test to police the Go/Nix script-assembly duplication that caused it — a sub-second `nix-instantiate` golden test does that job on every `go test ./...` run. Everything else in this review (a real silent-miscompile bug in `-include` handling, a sandbox-mode perf idea that turns out not to work as designed, several cheap regression tests, and some Nix-side dedup/cleanup) is real but secondary to that one gap.

## 2. Do first

**1. Add a fast `nix-instantiate`-based golden test for `script()` vs. `nix/{builder,linker,archiver}.nix`**
- Why now: it is the prerequisite for safely touching any of the byte-identity-critical files below, and for verifying fix #2 without a multi-minute run. Today `go test ./...` contains zero coverage of the Go/Nix agreement (`internal/expr/expr_test.go` only tests placeholder/nix32 helpers); the only check is `tests/drv-equivalence.sh`, which needs a builder-rpc-v0-capable patched Nix and a remote builder, and was independently confirmed to fail outright in this environment for lack of one.
- Concrete change: a Go test that shells out to `nix-instantiate --eval --strict --json -A args` against `nix/builder.nix`/`linker.nix`/`archiver.nix` with representative param sets (empty flags, `-l` flags, multi-input archive) and string-compares the result to `(*Derivation).script()` for the equivalent Go `Derivation`. Verified standalone: ~30ms, no daemon/store/builder-rpc-v0 needed.
- Effort: small.
- drv-hash risk: none — test-only, reads but never writes production script/args content.
- Unblocks: fix #2 below (verify without the slow integration path), the scan/link/wrapperenv regression tests in "Worth doing", and the larger dual-serializer refactor (also below), which the duplication lens explicitly says should land only after this exists.

**2. Fix native-mode flag quoting: it doesn't escape embedded single quotes; sandbox's Go quoting does**
- Why now: this is not a hypothetical — it's a demonstrated, present-day break of the core invariant. `internal/expr/expr.go:543-556`'s `shellQuoteFlags` produces `'-DFOO=it'\''s'` for a flag containing `'`; the hand-maintained counterparts at `nix/builder.nix:34` and `nix/linker.nix:37-38` (`map (f: "'${f}'") flags`) produce `'-DFOO=it's'` — an unbalanced quote that fails `bash -n` with a hard syntax error. Both sides consume the identical `Derivation.Flags` slice, so this is structural, not edge-case noise.
- Concrete change: apply the same `'` → `'\''` escaping in `nix/builder.nix` and `nix/linker.nix` (e.g. `builtins.replaceStrings ["'"] ["'\\''"] f`), ideally factored into one shared Nix helper so the two implementations can't drift apart again. Add a pinned test case for `shellQuoteFlags` with an embedded `'` (in the golden test from #1), and extend one `tests/drv-equivalence.sh` fixture to pass a flag with an embedded apostrophe, since none of the current four do.
- Effort: small.
- drv-hash risk: closes a divergence, does not create one. Verified the fix produces byte-identical output to Go's `shellQuoteFlags` on the same input, and since none of the 81 currently-pinned drvs have apostrophes in any flag, applying it invalidates zero existing pinned hashes. Before the fix, affected inputs aren't merely hash-divergent — native mode is outright broken (unparseable shell), so this is unambiguously a bug fix, not a cache-buster to worry about.
- Unblocks: closes the highest-severity open gap in the invariant the whole test suite exists to protect.

**3. Deduplicate the `-frandom-seed`/`-rpath` scrub between `preBuild` and `shellHook`**
- Why now: `nix/mkNixggBuild.nix:158-160` and `nix/mkNixggBuild.nix:205-207` (equivalently: lines 127-161 vs 194-217 in the nix-quality lens's broader anchors) contain byte-identical `sed` logic with no shared source. It isn't broken today (both copies were last edited together), but it is exactly the kind of hand-sync the project's own comments warn about elsewhere, and a future one-sided edit would only be caught by the slow, remote-builder-dependent integration test — or not at all.
- Concrete change: factor the scrub body into one `let scrubEnv = ''...'';` binding in `mkNixggBuild.nix`, interpolated into both `preBuild` and `shellHook`. Verified via `nix-instantiate --eval` that this reproduces byte-identical content in both places when whitespace is preserved carefully.
- Effort: small.
- drv-hash risk: none for the refactor itself, provided whitespace is preserved exactly (independently verified). Note the more precise mechanism: it's not the outer `stdenv.mkDerivation`'s own hash that's load-bearing here, it's that `preBuild` (sandbox path) and `shellHook` (native `nix develop` replay, used by `drv-equivalence.sh`) must produce identical `NIX_CFLAGS_COMPILE`/`NIX_LDFLAGS`, which then feed the inner tu-/link-/ar-drvs that are actually pinned.
- Unblocks: nothing else directly, but removes a latent trap in the file most responsible for keeping modes converged.

**4. Fix `-include <file>` being silently dropped / turned into a bogus `-I<file>`**
- Why now: this is a genuine silent miscompile, not a hash nit. `internal/shim/compile.go:361-386`'s `rewriteFlags` and `internal/scan/scan.go:311-331`'s `extractIncludeDirs` both put `-include` in the same `pathFlags` bucket as `-I`/`-isystem`, so a real `-include config.h` (the standard autoconf/CMake `HAVE_XXX` pattern) is deleted from the flags reaching the compiler, and `scan.go` may additionally emit a bogus `-I<path-to-a-file>`. The header still gets staged (scan's own `-MM -MG` sees it as a dependency), so the build *succeeds* — with different preprocessor state than requested, and zero error output.
- Concrete change: give `-include` its own case in both `extractIncludeDirs` and `rewriteFlags`/the iflags builder — resolve and stage the header, then re-emit `-include <staged-relative-path>` verbatim instead of dropping it. Add a regression test asserting a `-include foo.h` compile retains an `-include` flag in the emitted flags.
- Effort: medium.
- drv-hash risk: changes hashes uniformly in both modes for any TU using `-include` (both `compileDerivation` and `CompileJSON` consume the same `sandboxFlags` slice before serialization) — no divergence risk, and the hash change is the correctness fix taking effect, not a regression.
- Unblocks: nothing else, but this is the one finding most likely to bite a real downstream project (any autoconf/CMake build with a force-included config header) with no warning signal at all.

## 3. Worth doing

Ranked by payoff/effort; all confirmed, all drv-risk "none" unless noted.

- **Regression tests for three already-fixed historical bugs, currently untested** (small effort each, none risk): `scan.go`'s `callerDirs`/`projectRootHints` split (the ffmpeg `-Ilibavutil`-shadows-`<time.h>` bug, `scan.go:172-196,263-288` — not even exercised by `drv-equivalence.sh`, which has no ffmpeg fixture wired in); `parseLinkArgs`/`script()`'s objects-before-`-l`-flags ordering (the ffmpeg `-lm`/`-latomic` link-order bug, `link.go:143-198`, `derivation.go:135-169`); `wrapperenv.JSON()`'s empty-vs-nonempty trigger emission (`wrapperenv.go:56-67`, the exact "empty map produces differently-shaped output" bug class already fixed once in commit `fe671b4`). Each is a pure function, testable in milliseconds with `t.Setenv`/table cases, and each targets a bug that previously required a 45s+ build to notice. Sequence after item #1 above (same golden-test machinery/spirit).
- **Collapse link/archive's double input-classification** (`link.go:51-78`, `archive.go:39-64`, `expr.go:129-141,428-450`): both shims build two parallel lists (`[]expr.Input` for native, `[]expr.JSONDrvInput` for sandbox) from one `classify.Target` pass, then translate one into the other later. Classify once into `[]expr.Input`, delete `JSONDrvInput`/`inputsFromJSON`. Small effort, none risk if careful — must be re-verified against `drv-equivalence.sh` since a mapping slip would be easy to miss in native-only runs.
- **`classify` drvref-stub test, corrected scope** (`classify.go:82-132`): add tests for stub-file→`Kind==Drv` and plain-file→`Kind==Regular` (both independently verified to hold), and deduplicate the `#!nixgg-drvref` magic string, currently hardcoded identically in three places (`sandbox.go:103`, `classify.go:149`, `link.go:236/238`) with nothing enforcing sync. Drop the originally-proposed dangling-symlink test case — verified it does *not* reproduce the historical bug: `classify.Target` already classifies a dangling `.drv` symlink as `Kind==Drv` via an `EvalSymlinks`→`Readlink` fallback; the real historical failure was in a Makefile's shell-level `test -e`, a different layer entirely.
- **Extend the `mode.For` realise carveout to `Link` (and `Archive`)** (`compile.go:161-163` vs. `link.go`, which never imports `internal/mode`): `try_run`-style probes or two-step `cc -c && cc ... -o` probes that execute a link output today may exec a thunk symlink or drvref stub instead of a real binary. Medium effort, none risk (only changes *when* realisation happens, not derivation content).
- **`isLinkInput` gains `.so`/`.so.N`; `resolveLibFlag` handles `-l:exact-name`** (`link.go:241-246,205-225`): a positional shared library or `-l:libfoo.a` syntax currently falls through to being treated as an ordinary flag string, bypassing `classify.Target`'s passthrough safety net entirely. Small effort, none/uniform risk. Lower priority — confirmed rare in the current example set (none of hello/lua/fmt/mosh/redis/ffmpeg trigger it) but is exactly the "silently wrong, not loudly wrong" failure class worth closing before it's hit by a real project.
- **Widen `dispatch.FromArgv0` beyond the six exact basenames** (`dispatch.go:52-69`, `flake.nix:203-208`): triple-prefixed (`x86_64-linux-gnu-gcc`) or versioned (`gcc-15`) compiler names get no shim symlink at all, so acceleration silently never engages for that tool — no error, no drv, easy to miss. Small effort, none risk (`Tool.Basename()` still maps to the same six canonical values).
- **Dual-serializer unification: bake `script()`'s Go output into the native thunk instead of having `nix/{builder,linker,archiver}.nix` re-derive it** (`derivation.go:121-182,224-254`, `nix/linker.nix:28-42`): this is the actual root cause behind items #2/#3 above — the shell-assembly *algorithm* (not just the env/field shape) exists twice, in two languages, guarded only by discipline plus (now) the golden test. A real fix, but large effort: native `CompileParams`/`LinkParams`/`ArchiveParams` need the same concrete `Bash`/`Coreutils`/`Compiler`/`AR` store-path fields sandbox mode already carries. **Sequence strictly after item #1** (the golden test) so the migration's byte-preservation can be verified in seconds, not minutes. drv-hash risk is genuinely conditional, not "uniformly changes" as one lens claimed: a `.drv`'s hash depends only on the final `args`/`env` bytes, not on what computed them — if the migration reproduces today's Nix-computed `args` text exactly (which is the whole point and is achievable), risk is **none**; only a sloppy migration would cause divergence. Treat it as "none if verified byte-identical via #1 before merging, else risks divergence" — do not merge without that check passing.
- **Flake.nix example registry for the 5 uniform examples** (lua/fmt/mosh/redis/ffmpeg; `flake.nix:253-308,331-337`): fold the repeated `<x>Build = import ...; <x> = <x>Build.result;` / `<x>-shell = <x>Build.shell;` shape into a data table + `mapAttrs`, leaving llvm/two-phase/hello's bespoke multi-output wiring alone. Medium effort, none risk. Note: the actual removable boilerplate is closer to **10-15 lines**, not the "30-40 lines" originally claimed — two of the cited anchor lines (`hello-shell`, `llvm-shell`) aren't even in scope, and per-example `extraArgs` data (e.g. mosh's 9-line buildInputs list) still has to exist somewhere regardless of the refactor.
- **Document the fragility of the `-frandom-seed`/`-rpath` scrub against nixpkgs' exact output shape** (`mkNixggBuild.nix:140-161`): verified directly against a live nixpkgs checkout that the sed patterns match `reproducible-builds.sh` and stdenv's `_addRpathPrefix "$out"` output shapes exactly as they exist today; since the flake tracks `nixos-unstable`, a `nix flake update` could change either script's output and silently reintroduce per-run noise into every drv's env, with no signal besides a slow `drv-equivalence.sh` failure. Small effort (a comment, or an assertion) — makes that eventual failure fast to diagnose instead of a mystery. drv-risk: none now; the latent risk, if it ever fires, affects reproducibility symmetrically in both modes (not mode-divergence).
- **Two trivial doc/cleanup fixes**: `flake.nix:236-240`'s comment promises a `.#<name>-drv` attribute that was never wired up (only `<name>`/`<name>-shell` exist; `drv-equivalence.sh` consumes `-shell`) — fix the comment. `dyn-drv/lua-mkbuild.nix` is dead (unreferenced anywhere except a stale ARCHITECTURE.md listing, superseded by `examples/lua`, pins its own disconnected hash) — delete it. Note `hello-mkbuild.nix` is *not* dead (still imported at `flake.nix:241`) and the other `dyn-drv/*.nix` files are deliberate documentary teaching examples, not dead code — leave those alone.
- **A `phaseChain`-style helper for multi-target builds** (LLVM's 3-phase workaround, `examples/llvm/default.nix:99-149`): each phase re-specifies near-identical `cmake`/`ninja` boilerplate differing only in target and one flag. This is a known, already-documented gap (ARCHITECTURE.md's "What we don't (yet) do"), and the workaround is functional today, so this is lowest urgency of the "worth doing" items despite being a real, growing pain point (two-phase.nix's own comments predict protoc/rustc-stage use cases). Large effort, none risk if the helper only generates the same `mkNixggBuild` calls examples currently hand-write.

## 4. Considered and rejected

- **Content-addressed cache in front of `nix derivation add`/`nix store add --scan` for sandbox-mode warm rebuilds** (`compile.go:206,259`, `sandbox.go:34-74`). The per-call timing claim (~44-90ms/call fork+exec overhead) was independently reproduced and is real, and it does match a gap ARCHITECTURE.md already names. But the proposed `.nixgg/`-relative file cache **does not work as designed**: sandbox-mode shims run exclusively inside a fresh, ephemeral builder-rpc-v0 sandbox per top-level `nix build` (confirmed no `sandboxPaths`/bind-mount of any persistent host directory in `mkNixggBuild.nix`, and `dontUnpack = false` means `src` is freshly unpacked every build). Any cache state the shim writes is discarded when that build ends and is never seen by the next `nix build` invocation — the one place the redundant work would need to be amortized. A working version would require bind-mounting a stable host cache directory plus reasoning about sandbox isolation and build concurrency, which pushes effort well past "medium." Rejected as stated; revisit only alongside that additional infrastructure.
- **Raw Nix-worker-protocol batching for `derivation add`** (to avoid per-call fork/exec entirely). Confirmed the CLI genuinely has no batch mode (`nix derivation add` on two concatenated JSON docs fails with a JSON parse error), and `dyn-drv/NOTES.md` already explicitly rejected writing a raw-protocol client in favor of shelling out to the CLI. The recommendation to skip this stands, but not for the reason originally given (that the file-cache above "already captures the win" — it doesn't, per the rejection above). Reject on its own cost/uncertain-payoff grounds: it would duplicate nix-ninja's Rust worker-protocol client for a benefit that's unproven without the cache actually working, and cold-build cost is bounded by real compiler work anyway.

## 5. Already healthy

- The dual-serializer design itself (one `Derivation` struct, `ToNix`/`toJSON` split by `Kind`) is sound and keeps the env dict, field set, and `StoreDeps`/`WrapperEnv` handling in lockstep between modes — do not restructure this wholesale; the real duplication is narrower (script-assembly algorithm + input classification, addressed above).
- `nix/{builder,linker,archiver}.nix` and `pure-store-path.nix` are small, focused, well-commented, with no meaningful complexity beyond the quoting bug already flagged.
- `examples/*/default.nix` (lua, fmt, mosh, redis, ffmpeg) are load-bearing and well-commented, not boilerplate needing a shared helper — every non-obvious flag (redis's `SOURCE_DATE_EPOCH`, mosh's `--disable-dependency-tracking`, ffmpeg's `--disable-x86asm`) has inline rationale tied to a real failure.
- `internal/scan`'s mtime-keyed cache already avoids the `gcc -MM -MG` fork on a hit — this is the fix ARCHITECTURE.md asked for on the compile-scan side, and it's already done.
- `internal/stage`'s hardlink-reuse check (2 stats + 1 `WalkDir` per staged entry) is 2-3 orders of magnitude cheaper (sub-millisecond at LLVM scale) than the process-spawn cost downstream of it — not a target worth optimizing.
- No O(n²) behavior found in the shim hot path at LLVM/ffmpeg-relevant TU counts; everything in `compile.go`/`link.go`/`archive.go` is linear per invocation.
- `dyn-drv/{config,dyn-one-layer,dyn-json-drv,nixgg-sandbox}.nix` are deliberate documentary/exploratory files (each teaches a distinct mechanism not otherwise visible through `mkNixggBuild`'s scaffolding) — not dead code, unlike `lua-mkbuild.nix`.
- The `out = "/nonexistent"` trick in `mkNixggBuild.nix:71` is a deliberate, well-precedented tradeoff (cites nix-ninja's identical pattern) with no cleaner alternative short of reimplementing large parts of stdenv's phase machinery — leave as is.
